Escopo
& Objetivos

o problema · o que está dentro · o que ficou fora · o caso de uso

Escopo do problema

Áudio enviado por usuário é caro, opaco e lento

É grande

Um WAV de 5 minutos passa de 40 MB. Guardar o formato bruto multiplica custo de disco e de banda em toda leitura posterior.

É opaco

Áudio não é pesquisável nem escaneável. Para saber o que há dentro, alguém precisa ouvir do começo ao fim.

É lento de processar

Transcodificar e transcrever custa segundos a minutos por arquivo — muito mais do que uma requisição HTTP deveria durar.

O erro comum é resolver os três dentro do POST: o cliente fica pendurado esperando ffmpeg e o modelo, o timeout estoura, e um pico de uploads simultâneos derruba o servidor.
Delimitação

O que está dentro — e o que ficou fora de propósito

Dentro do escopo

Recepção e validação de áudio via multipart/form-data
UUID + URL + metadados persistidos, bytes no file store
Compressão para AAC em worker paralelo
Resumo ≤ 500 caracteres com IA local
Cliente web que envia e acompanha o resultado
Swagger + arquivo .http como contrato executável

Fora do escopo — e por quê

Autenticação / multi-tenancy — o foco é o pipeline de mídia
S3 / Azure Blob — IFileStore já isola; o local basta
Transcrição paga — o requisito é modelo leve e local
Retry automático — áudio inválido é falha permanente
Migrations — EnsureCreated(), domínio estável

Funcionais

F3 Comprimir para AAC sem bloquear a requisição

Não funcionais

N2 Sob carga, degrada com 503 — não cai
N3 Compressão usa todos os núcleos disponíveis
N4 Escritas concorrentes nunca corrompem o banco
N5 Shutdown não perde trabalho — recupera no start
N6 API documentada e testável sem cliente
Caso de uso

"Enviar um áudio e saber o que tem dentro"

Ator: pessoa com uma gravação em mãos que quer saber o conteúdo sem ouvir tudo.

Fluxo principal

1 Arrasta o arquivo no cliente web (:3000)
2 Front faz POST /api/audios
3 API valida, reserva vaga, grava e responde 201
4 Tela já mostra a mensagem "processando"
5 Workers comprimem e resumem em background
6 Polling troca a mensagem pelo resumo

Fluxos alternativos

400 Não é áudio (nome / content-type / tamanho)
503 Filas saturadas — nada é persistido
201 Passa na validação mas o ffmpeg não decodifica → Failed depois
201 Worker de resumo fora do ar → áudio segue armazenado, tela diz o motivo
↻ Processo cai no meio → job volta a Pending e é reenfileirado

Pipeline

Do upload ao resumo — cinco estágios

Estágio 01 Recepção
multipart/form-data
valida nome, tipo, tamanho
inválido → 400
Estágio 02 Admissão
reserva vaga na fila
grava bytes + linha
sem vaga → 503
Estágio 03 Resposta
201 Created + Location
UUID, URL, Pending
~0,2 s para 42 MB
Estágio 04 Compressão
ffmpeg → AAC .m4a
apaga o original
N núcleos em paralelo
Estágio 05 Resumo
Whisper tiny local
≤ 500 caracteres
front faz polling
Estágios 01–03 são a requisição HTTP e terminam em ~0,2 s
Estágios 04–05 são background — nada de ffmpeg ou IA dentro do POST
Pipeline

Caminho da requisição × caminho do trabalho

Síncrono — dentro da requisição

POST /api/audios Validar Reservar vaga File store INSERT 201 Created

Assíncrono — em background, depois da resposta

Fila de compressão ffmpeg → .m4a Apaga original Fila de resumo Whisper Resumo ≤ 500
Ponte entre os dois: GET /api/audios/{id}/summary em polling — Pending → Processing → Completed | Failed. O polling para sozinho quando todos os áudios chegam a um estado final.
Pipeline

Modelo de concorrência — uma primitiva por gargalo

EtapaPrimitivaGrauPor quê
Admissão Channel<Guid> bounded + reserva 100 Backpressure explícito: sem vaga, responde 503 antes de escrever qualquer coisa
Compressão Parallel.ForEachAsync ProcessorCount CPU-bound — escala com os núcleos da máquina
Resumo SemaphoreSlim 1 I/O contra uma VPS de 4 vCPUs; mais paralelismo só atrasa todo mundo
Escrita no banco DbWriteGate — SemaphoreSlim(1,1) 1 SQLite aceita um escritor por vez, e dois workers escrevem no mesmo arquivo
Por que não DropWrite: o runtime retorna true mesmo quando descarta o item novo — uma mentira silenciosa. A reserva prévia é o que garante que um 503 não deixe arquivo nem linha órfãos.
Pipeline

Política de falhas — cada exceção tem um dono

Classe realPolítica
OperationCanceledException
token do host cancelado		 Não é falha do áudio: volta a Pending, propaga o cancelamento e é recuperado no próximo start
AudioCompressionException
ffmpeg terminou ≠ 0		 Falha permanente do item: marca só aquele áudio como Failed e segue para os próximos
FileNotFoundException
do arquivo específico		 Falha conhecida do item: mensagem pública sem caminho e continuação da fila
Demais IOException, Win32Exception,
DbUpdateException, não classificados		 Potencialmente sistêmico: log Critical, exceção fatal sanitizada, terminalização best-effort
Sem retry automático — de propósito. Áudio inválido é falha permanente, e o projeto não tem critério seguro de idempotência para filesystem ou SQLite. Retry cego só multiplicaria o mesmo erro.

A tela é uma conversa

Comportamento

Cada áudio processado vira uma mensagem com o seu resumo
As 10 mais recentes abrem a conversa, antes da sessão atual
Sem resumo ainda? A mensagem diz o motivo — comprimindo, falhou, aguardando ou desativado
Nenhum estado renderiza corpo vazio
Polling roda só com áudio não-terminal e para sozinho

Resultados

O que foi medido

2,9s → 0,2sPOST de um WAV de 42 MB
≈14xGanho na resposta
43Testes xUnit verdes
0Testes que precisam de rede

Cobertura

Integração ponta a ponta com WebApplicationFactory — upload → GET → download já em AAC
Truncamento do resumo em 10 cenários — nunca passa de 500, nem parte emoji ao meio
Fila e cancelamento do worker paralelo
Vitest + RTL no cliente; gate em Docker sem rede e non-root

Garantia dos 500 caracteres — em 3 camadas

No worker, ao gerar o resumo
Na API, em SummaryTruncator.Clamp
Na coluna do banco, com HasMaxLength(500)
Nenhuma camada confia na anterior — com um stub devolvendo 5.000 caracteres, o resultado ainda sai com ≤ 500
Trade-offs

Decisões de arquitetura

DecisãoAlternativa rejeitadaMotivo
Processar em background Comprimir e transcrever no POST Transcrição escala com a duração do áudio (~10x tempo real) — 50 MB levaria minutos
Duas filas separadas Uma fila para as duas etapas Perfis opostos: compressão é CPU-bound e paralela; resumo é I/O-bound e serial
Reservar vaga antes de gravar Gravar e depois enfileirar Sem reserva, um 503 deixaria arquivo e linha órfãos no disco
IFileStore como abstração Escrever no disco direto no endpoint Permite trocar por S3/Blob sem tocar nos endpoints
Whisper tiny local API paga de transcrição Requisito de IA leve e local; roda offline após o primeiro download dos pesos
SQLite Postgres Escopo acadêmico: um arquivo, zero setup. O DbWriteGate é o preço pago
Isto é o oposto da conclusão da semana 2 — de propósito. Lá, comprimir custava 160 ms e não valia um worker. Quando o resumo entrou (1435 ms, ~9x mais caro), o custo mudou de ordem e a decisão junto.
